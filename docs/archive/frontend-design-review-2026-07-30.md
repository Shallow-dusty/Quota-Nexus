## 0. 审议规则

Kimi 应逐项填写“接受 / 修订后接受 / 拒绝”，并给出可复核理由。不要因为概念图已经画出
某个元素就默认接受，也不要整文件重写本提案。优先检查：

1. 方案是否服务“多供应商、多账号额度监控”的真实信息层级。
2. 是否错误假设三家额度可以换算或相加。
3. 是否存在 MVP 不需要的页面、组件或依赖。
4. Liquid Glass 是否影响长时间阅读、键盘操作、性能或 Windows 一致性。
5. 前端契约是否能容纳加载、陈旧、部分失败、认证过期和窗口缺失等真实状态。
6. 实现顺序是否会在 Provider 合同未验证前制造返工。

用户已经明确：目标平台仍是 Windows；“Liquid Glass”只描述 UI 风格，与 macOS/iOS
平台无关。这一点不是待辩议项。

## 1. 设计目标与非目标

### UI-P01：用三层材质体系表达层级，不做全屏玻璃化

**提案**

前端只定义三类表面：

| 表面 | 用途 | 视觉强度 |
| --- | --- | --- |
| `StableSurface` | 额度卡、趋势图、表格、表单主体、长文本 | 低透明或不透明，保证对比度 |
| `ControlGlass` | 侧栏、顶部工具栏、筛选条、分段选择器 | 中等透明与柔和高光 |
| `FloatingGlass` | Tooltip、Popover、菜单、Toast、Dialog、命令面板 | 最强玻璃感，但面积小、停留短 |

窗口背景可以在 Windows 11 上使用 Mica 作为氛围底层；不支持或性能不合适时退化为静态
渐变与半透明色。应用内容不依赖 Mica/Acrylic 才能辨认。

**理由**

- 额度监控是数据产品，主要任务是快速比较状态而非欣赏材质。
- 大面积 `backdrop-filter` 会增加 GPU 合成成本，也会让图表、文字和状态色失去稳定背景。
- 把玻璃集中在控制层和浮层，仍能保留概念图的通透、边缘高光与空间感。
- Windows 材质作为渐进增强，不会把 UI 与某个系统版本绑定。

**请 Kimi 重点审核**

- 三类表面是否已经足够，还是需要进一步合并。
- Mica 是否应在 MVP 中启用，或仅保留设计 token，发布硬化阶段再接入。

### UI-P02：视觉语义优先于“像苹果”

**提案**

产品视觉描述统一为：

> 受 Liquid Glass 启发的 Windows 桌面半透明层级与微交互系统。

不使用 macOS 红黄绿窗口按钮，不照搬 macOS 设置页导航，不把 Apple 原生材质/API 写成
本项目能力。可借鉴的只有：

- 光照感边缘与柔和高光。
- 浮层之间清楚的深度关系。
- 连续圆角、克制阴影和小幅弹性反馈。
- 控件状态变化时的流体过渡。

**理由**

- 用户要的是风格，不是平台仿制。
- 真实 Windows 桌面行为、快捷键、通知、托盘和高 DPI 支持更重要。
- 清楚定义借鉴边界可避免后续设计评审不断争论“是否足够像 mac”。

## 2. 信息架构

### UI-P03：MVP 只实现三个一级页面

**提案**

MVP 一级导航仅保留：

1. **概览**：查看全部账号、关键状态、刷新与筛选。
2. **账号与连接**：录入账号、凭据、Workspace，验证连接、暂停监控。
3. **设置**：刷新周期、托盘、自启动、通知阈值、历史保留和隐私显示。

以下能力不作为独立 MVP 页面：

- **趋势/洞察**：在概览中先提供一个可折叠趋势区；有足够历史数据后再独立成页。
- **告警**：简单全局阈值先放设置；出现账号级/窗口级复杂规则后再独立成页。
- **诊断**：MVP 先通过账号详情抽屉和设置中的诊断区承载；信息量增长后再独立。
- **预算/成本**：没有稳定、同口径的上游金额数据前不建页面。
- **全局搜索与工作区切换**：单用户本地 MVP 没有足够对象规模，不提前实现。

**理由**

- 当前核心闭环是“添加账号 → 成功读取 → 在概览判断状态 → 收到告警”。
- 五至七个空页面会稀释主线，并迫使我们为还不存在的数据设计假功能。
- 先以区块/抽屉承载次级能力，内容增长后提升为页面，比先做空壳更可逆。

**请 Kimi 重点审核**

- 诊断是否因 Provider 不稳定性而应从首版起独立成页。
- 告警规则是否放在设置会造成信息架构混杂。

### UI-P04：概览不展示跨供应商“总剩余额度”

**提案**

概念图顶部的 `2,847,320 / 5,200,000 Tokens` 不进入真实设计。Hero 区改为四项可比较
且不会伪造统一单位的摘要：

1. 正常账号数 / 已启用账号数。
2. 当前最高使用率窗口（账号 + 窗口 + 百分比）。
3. 最近一次重置（账号 + 倒计时）。
4. 最后一次全局刷新及失败数。

账号卡仍分别展示供应商原生的窗口与单位。只有当一个供应商明确返回同口径绝对值时，
才在该账号/该窗口内部显示绝对用量。

**理由**

- Session、5 小时、周、月窗口不可相加。
- token、美元额度、请求数和百分比也不可相加。
- “总余额”视觉冲击力强，但会制造不存在的业务含义。

### UI-P05：概览使用“摘要条 + 账号卡网格 + 可折叠趋势”

**提案**

桌面宽屏布局：

```text
┌────────侧栏────────┬──────────────────内容───────────────────┐
│ 概览               │ 页面标题     筛选/排序      刷新/设置    │
│ 账号与连接         ├─────────────────────────────────────────┤
│ 设置               │ 状态摘要条（4 项，不合计异构额度）       │
│                    ├─────────────────────────────────────────┤
│                    │ 账号卡网格（2–3 列，自适应）             │
│                    │ [账号 A] [账号 B] [账号 C]               │
│                    ├─────────────────────────────────────────┤
│                    │ 历史趋势（有数据时显示，可折叠）          │
└────────────────────┴─────────────────────────────────────────┘
```

窗口变窄时，侧栏折叠为图标栏，账号卡退化为单列；不为手机触控布局做额外断点。最小支持
窗口暂定 `960 × 640`，设计验证后再锁定。

**理由**

- 多账号对比是最高频动作，卡网格比大表更适合 5–15 个账号。
- 摘要条给出“是否需要行动”，账号卡给出“哪个窗口需要行动”。
- 趋势需要历史数据，不应在首次启动空状态中占据主要空间。

## 3. 额度卡与状态语义

### UI-P06：`ServiceQuotaCard` 是首个领域组件

**提案**

每张额度卡包含：

- 供应商图标、账号标签、套餐（有则显示）。
- 综合健康徽标：正常、接近上限、认证失效、数据过期、连接错误、已暂停。
- 上次成功刷新时间与数据新鲜度。
- 1–3 个 `QuotaWindowRow`，按风险降序排列。
- 卡片级手动刷新和更多操作菜单。
- 失败时保留最后成功值，但用明确的陈旧遮罩/说明，不用空白替换。

每个 `QuotaWindowRow` 包含：

- 窗口名。
- 已用百分比和剩余百分比（二者文案固定，不在不同页面互换方向）。
- 线性进度条。
- 重置倒计时；未知时直接显示“重置时间未知”。
- 阈值状态图标 + 文本。

默认不把圆环作为每个窗口的主表达。一个账号多个窗口时，线性行更容易纵向比较；圆环只可
作为卡片中“当前最危险窗口”的增强视图，且不取代文字与进度条。

**理由**

- 三家供应商的窗口数量并不相同，固定一个圆环会隐藏信息。
- 概念图中的大圆环适合单 KPI，但多窗口额度需要高信息密度。
- 保留最后成功值是项目已有可靠性要求，前端必须把“值”和“新鲜度”分开表达。

**请 Kimi 重点审核**

- 是否完全取消卡片圆环，从而降低视觉噪声与开发量。
- 卡片默认排序应按“最危险窗口”还是用户固定顺序。

### UI-P07：状态不能只靠颜色，颜色也不能表示 Provider

**提案**

- Provider 品牌色只用于图标或非常小的装饰，不承担健康含义。
- 健康色固定：正常、提示、警告、危险、中性/陈旧。
- 每个状态同时具备图标、短文本和必要的辅助说明。
- 进度条采用状态色，但百分比和状态词始终可见。
- 色彩 token 需分别验证浅色、深色和 Windows 高对比模式。

**理由**

- 如果蓝/紫/绿既表示供应商又表示健康，用户无法快速判断状态。
- 色弱和高对比模式下必须仍可识别。

### UI-P08：明确首屏的五种数据状态

**提案**

所有页面和领域组件从一开始覆盖：

1. `initial-loading`：骨架屏，不显示伪造数字。
2. `ready`：展示成功数据。
3. `refreshing`：保留现有数据，仅在局部显示刷新状态。
4. `stale-with-error`：保留最后成功值，显示失败原因与最后成功时间。
5. `empty`：解释下一步并提供“添加账号”主按钮。

认证失效属于可操作错误，必须直接给“更新凭据”入口；解析器变化属于系统错误，给诊断入口，
不要求用户反复重录凭据。

**理由**

- 额度抓取依赖非稳定页面，部分失败将是常态，不是边缘情况。
- 若不先设计状态矩阵，静态概念图落地后通常只拥有漂亮的成功态。

## 4. 必要组件与增强组件

### UI-P09：组件分为四层，按依赖顺序实现

**提案**

第一层，设计基础：

- color / spacing / radius / typography / elevation / motion tokens
- `StableSurface`
- `ControlGlass`
- `FloatingGlass`
- `GlassFallback`

第二层，通用控件：

- `Button`、`IconButton`
- `TextField`、`PasswordField`、`Select`、`Switch`
- `SegmentedControl`
- `Tooltip`、`Popover`、`DropdownMenu`、`Dialog`
- `Toast`
- `StatusBadge`
- `ProgressBar`
- `Skeleton`、`EmptyState`、`ErrorState`

第三层，额度领域：

- `ServiceQuotaCard`
- `QuotaWindowRow`
- `AccountHealthBadge`
- `RefreshControl`
- `AccountEditor`
- `CredentialField`
- `ProviderConnectionTest`
- `TrendChart`

第四层，体验增强：

- 截图隐私模式。
- Command Palette / 全局搜索。
- 卡片重排与个性化布局。
- 更复杂的预测、热力图、成本图。
- 纯装饰的 3D 玻璃物件和动态光晕。

前三层中未被首批页面使用的组件不提前创建。第四层不进入 MVP 关键路径。

**理由**

- “从基础组件到必要业务组件”可以形成可测的依赖链。
- 明确增强层能防止概念图中的装饰元素绑架实现优先级。
- 不创建未使用空壳，符合项目现有 Phase 0 原则。

### UI-P10：交互必须先有键盘与减少动态方案

**提案**

- 所有控件使用可见焦点环，遵循 Tab 顺序，Popover/Dialog 正确管理焦点。
- 全局刷新快捷键建议 `Ctrl+R`，但需阻止 WebView 页面重载语义。
- `Esc` 关闭最上层浮层。
- Tooltip 不承载唯一信息；键盘聚焦也可触发。
- 遵守 `prefers-reduced-motion`：取消位移、弹性和背景漂移，只保留短淡入淡出。
- 普通过渡 120–180ms；状态布局变化 180–240ms；不做持续循环玻璃动画。

**理由**

- 桌面工具的高频用户会依赖键盘。
- Liquid Glass 风格若没有减少动态策略，容易变成持续干扰。

## 5. 技术栈

### UI-P11：采用“可访问行为库 + 自有视觉层”，不把 shadcn 默认样式当设计系统

**提案**

| 职责 | 选择 |
| --- | --- |
| 桌面壳 | Tauri 2 + Rust |
| UI | React + TypeScript + Vite |
| 样式 | Tailwind CSS 4 + CSS variables + 自有材质 classes |
| 无障碍行为 | React Aria Components |
| 组件源码脚手架 | shadcn/ui，可选且逐组件引入 |
| 动效 | Motion for React，仅用于必要过渡 |
| 服务端状态 | TanStack Query |
| 表单 | React Hook Form + Zod |
| 图表 | Apache ECharts，优先 SVG renderer |
| 图标 | Lucide |
| 测试 | Vitest + Testing Library + Rust 单元/集成测试 |

具体约束：

- React Aria 负责键盘、焦点、ARIA 和复杂控件行为。
- shadcn 只提供可拥有源码的起点，必须套用本项目 tokens，不直接继承其默认视觉。
- Tailwind 负责布局和 token 映射；玻璃材质用少量集中 CSS class 实现，避免组件内堆叠
  任意 backdrop/shadow 数值。
- TanStack Query 只管理前端对 Tauri command 的异步状态、缓存失效和刷新体验；额度事实
  与调度仍由 Rust Core/SQLite 拥有。
- ECharts 的 tooltip 必须有可访问的表格/摘要替代；趋势图只在历史数据实际存在后加载。

**理由**

- 可访问交互自己从零写成本高、缺陷隐蔽，React Aria 与“自定义视觉”兼容。
- shadcn 源码可控，但若把它当完整设计系统，很容易得到常见 SaaS 外观而非本项目材质。
- TanStack Query 能处理局部刷新和 stale UI，但不能成为第二个业务事实源。
- SVG 更适合本应用相对有限的数据点、高 DPI 和可交互文本；若长历史数据性能不足再切 Canvas。

**请 Kimi 重点审核**

- React Aria 与 shadcn 同时存在是否增加不必要的组件策略分裂；是否应只保留其一。
- TanStack Query 对 Tauri IPC 是否过重，是否可先用轻量 typed store。
- ECharts 对单一趋势图是否过重，是否改用更轻的图表库或自绘 SVG。

### UI-P12：Windows 窗口材质只做渐进增强

**提案**

- Windows 11：可选 Mica 背景，关闭透明效果或远程桌面时自动回退。
- Windows 10 或不支持环境：使用不依赖背景采样的静态渐变和不透明表面。
- 不在长列表、图表画布和表单主体使用 Acrylic。
- 视觉回归测试至少覆盖透明效果开/关、浅/深色、高 DPI、窗口聚焦/失焦。

**理由**

- 系统透明效果受用户设置、显卡、远程桌面和系统版本影响。
- 可回退方案是材质系统的一部分，不是发布前补丁。

## 6. 页面交互

### UI-P13：添加账号使用分步 Dialog，不做独立向导页

**提案**

流程：

1. 选择 Provider。
2. 展示该 Provider 所需字段与最小获取说明。
3. 输入账号标签、Workspace（如需要）和凭据。
4. 本地提交后立即执行连接验证。
5. 成功则保存并进入概览；失败保留非秘密字段，清空秘密字段，并显示错误分类。

账号与连接页用于后续编辑、暂停、刷新、更新凭据和查看连接健康。完整秘密永不回显。

**理由**

- 三家录入字段不同，分步结构能减少一次显示的复杂度。
- 添加账号是短任务，Dialog 完成后能自然回到账号列表。
- 连接验证是闭环的一部分，不能保存后让用户去概览猜测是否成功。

**请 Kimi 重点审核**

- 凭据获取说明是否应放右侧帮助面板，避免 Dialog 过高。
- 失败后清空秘密字段是否造成重复粘贴负担；是否应仅保留在当前前端内存直至 Dialog 关闭。

### UI-P14：刷新是局部可解释的，不用全屏 Loading

**提案**

- 顶部刷新按钮触发全局刷新，展示 `已完成 x/y`，但现有卡片不消失。
- 单张卡可独立刷新。
- Provider 熔断时，该 Provider 卡片统一提示而其他卡继续更新。
- 刷新按钮在任务进行中变为停止视觉反馈，但 MVP 不承诺真正取消已发出的 HTTP 请求；
  文案应为“刷新中”，不能显示虚假的“可取消”。
- Toast 只报告跨页面结果或需要行动的问题；普通成功刷新不弹 Toast。

**理由**

- 后台刷新与部分失败是核心行为，整页 Loading 会掩盖有效的最后成功数据。
- 过多成功 Toast 会让常驻监控工具产生噪声。

## 7. 数据契约

### UI-P15：前端只依赖脱敏 View Model，不直接复用数据库对象

**提案**

Rust Core 对 UI 输出页面专用 DTO，例如：

```ts
interface AccountQuotaView {
  accountId: string;
  providerId: ProviderId;
  displayLabel: string;
  maskedExternalScope?: string;
  plan?: string;
  health: AccountHealthView;
  windows: QuotaWindowView[];
  lastSuccessAt?: string;
  freshness: "fresh" | "stale" | "unknown";
  refreshState: "idle" | "queued" | "refreshing";
  availableActions: AccountAction[];
}
```

`availableActions` 由 Core 根据账号与适配器状态返回，UI 不根据错误字符串猜测能否重试、
更新凭据或查看诊断。秘密录入使用单独的一次性 command 参数，不进入 Query cache、
全局 store 或持久化前端状态。

**理由**

- 数据库模型、领域模型和显示模型的变化速度不同。
- Core 统一决定可用动作，能避免多个页面复制错误映射。
- 凭据不进入普通 UI 状态树，更容易审计泄露面。

## 8. 实施顺序

### UI-P16：先做可验证的纵向切片，不等“后端全部完成”再做前端

**提案**

实施顺序：

1. **Phase 0 Provider 探针**：确认三家真实额度合同。
2. **前端基础**：tokens、三类 surface、最少通用控件、静态状态矩阵。
3. **单 Provider 纵向切片**：一个真实 Adapter → Core DTO → 一张真实额度卡 → 手动刷新。
4. **账号闭环**：AccountEditor → 安全存储 → 验证连接 → 账号与连接页。
5. **多 Provider 概览**：补齐其余 Adapter、排序、筛选、部分失败。
6. **设置与后台行为**：周期刷新、托盘、自启动、阈值。
7. **历史与通知**：趋势区、Toast/Windows 通知和告警规则。
8. **视觉硬化**：Mica、深色、高对比、减少动态、性能与高 DPI。

不选择“后端全部完成后才画前端”，也不选择“先把所有页面静态设计完再接数据”。

**理由**

- Provider 返回字段尚未实证，过早冻结完整页面会返工。
- 完整后端先行会推迟发现 DTO、错误态和交互闭环问题。
- 单 Provider 纵向切片能尽早验证 Tauri IPC、秘密流向、状态矩阵和真实视觉密度。

**请 Kimi 重点审核**

- 第 2 步是否应推迟到第一个 Provider 探针成功之后再开始。
- 第一个纵向切片应选合同较稳定的 ClinePass，还是最具代表性的 OpenCode Go。

#### R-01（UI-P01）：玻璃感的可执行定义

用户的核心诉求是“液态玻璃风格”，三层材质是正确骨架，但骨架不保证成品好看。

- backdrop blur 半径与 saturate 比例区间；
- 背景不透明度下限（由 WCAG AA 对比度反推，正文 4.5:1，以最差壁纸背景实测）；

### 12.2 R-01：接受，但“最差背景”限定为受支持的应用合成状态

接受材质参数表作为 Layer-1 必交付物，也接受正文至少 4.5:1 的 WCAG AA 门槛和 Mica
推迟到视觉硬化阶段。

将“以最差壁纸背景实测”修订为：

> 对每种 surface × 浅色/深色 × 聚焦/失焦 × 系统透明开/关组合，使用应用允许透出的
> 最亮、最暗背景样本测试最终合成颜色。正文对比度至少 4.5:1；无法保证时自动提高表面
> 不透明度或启用 `GlassFallback`。不对任意、未受控的外部壁纸像素直接承诺固定透明度下
> 的对比度。

理由：对比度必须针对最终合成结果验证；但“任意最差壁纸”没有有限边界，无法形成稳定
测试夹具。应用应通过遮罩、底色下限和 fallback 把输入背景收敛为可测范围。

材质参数表先记录 token 名、允许区间、fallback 和对比度结果；具体数值由高保真原型与
视觉回归锁定，不能在没有渲染证据时仅凭文档拍定。

### 12.3 R-02：接受诊断能力保留清单

合并时采用用户可理解的 View Model 语义，不把数据库列名直接暴露为 UI 文案：

- 账号详情：下次允许重试时间、最近错误类别、连续失败次数。
- 设置诊断区：Provider 健康、熔断状态、最后成功时间和下一次探测时间。
- 账号卡仅显示行动相关摘要，完整细节进入账号详情，避免概览过载。
- 脱敏诊断导出仍按 Phase 4 交付。

这保留了“失败可解释”，同时没有为了诊断增加第四个一级页面。

### 12.4 R-03：接受单一行为层，修订 shadcn、Query 与图表裁决方式

#### 组件行为

同意全项目只允许一套行为原语：React Aria Components。不同意“shadcn/ui 当前必然封装
Radix，因此只能完全出局”这一事实前提。

截至 2026-07，shadcn/ui 已把 React Aria 作为 first-class component base，可通过
`shadcn init --base aria` 生成 React Aria 实现。因此合并文本应为：

> React Aria Components 是唯一行为原语库。shadcn CLI 仅可用 `aria` base 按需生成
> 由项目拥有的组件源码；禁止引入同功能的 Radix/Base UI 版本。生成代码必须经过本项目
> tokens、DOM/焦点语义和依赖审查，不把 shadcn 默认样式当作设计系统。

这样既消除双行为库，也保留成熟的源码脚手架，不必重复实现每个 React Aria 组合组件。

#### TanStack Query

接受 Kimi 的两条规则，并增加“Rust 调度器是唯一刷新时钟”：

- Query cache 只存 Tauri command 返回的脱敏 DTO。
- Tauri 事件通过 `setQueryData` 或 `invalidateQueries` 汇入同一 cache，不另建业务事实
  store。
- 关闭 `refetchOnWindowFocus`、`refetchOnReconnect` 和 Query 自带轮询；默认
  `staleTime: Infinity`，刷新由 Rust 调度、用户 command 或明确 Tauri 事件驱动。
- Query 的 `stale` 不是领域数据的 `freshness`；后者只能使用 Core 返回值。
- Dialog、筛选、展开状态等纯 UI 本地态不进入 Query cache。

理由：TanStack Query 的默认窗口聚焦/重连行为可能绕过 §6.2 调度、退避和熔断合同，必须
显式关闭。

#### 图表

接受“能力 + 预算”而非提前锁库：

- SVG 渲染。
- 同等信息的文本/表格替代。
- 动态 import，趋势区首次展开时加载。
- 以实际 production build 的增量 chunk 为准，目标不超过 120KB gzip。

Recharts 可作为首个 spike 候选，但不写入长期实现合同。其官方当前 tree-shaken 示例约
90.10KB gzip，表明有机会满足目标；最终仍须用本项目实际折线、轴、图例、Tooltip 和
无障碍替代实现测量。若超预算或交互不足，再比较 visx 或 `echarts/core` 按需构建。

### 12.5 R-04：接受凭据复用，取消秘密派生尾缀

添加账号第 3 步改为：

```text
凭据来源
├─ 使用已有凭据：同 Provider 的凭据标签 + 已关联账号数 + 最后验证时间
└─ 新建凭据：凭据标签 + 秘密输入
```

选择已有凭据时只提交 `credential_id`，不读取或传输秘密。列表不展示“脱敏尾缀”：

- API Key / Cookie 尾部仍是秘密的派生片段，没有必要扩大显示面。
- `Credential.label` 已是一等识别字段；关联账号数和最后验证时间足以消歧。
- 若用户标签重复，UI 提示修改标签，而不是依赖秘密片段补救。

新建凭据验证失败后，秘密只保留在当前 Dialog 组件的受控局部内存中；不进入 Query
cache、URL、日志、持久化 store 或开发诊断。成功、切换到已有凭据、取消或关闭 Dialog
时立即清空。帮助说明使用右侧面板；窄窗口下改为同 Dialog 内可折叠帮助区，不能强制
依赖 `≥720px` 的 Dialog 宽度。

### 12.6 R-05：接受 ClinePass 首切片

首个纵向切片选 ClinePass，可以把 API 解析风险与 IPC、安全存储、SQLite、DTO 和卡片
渲染风险解耦。补充前置条件：

> Phase 0 必须先实证 ClinePass 当前 host、path、认证 Header 和响应字段。若实证结果
> 表明其合同已变化或不可用，则按“已验证合同最稳定”的 Provider 重新选择，而不是为了
> 遵守文档继续硬做 ClinePass。

### 确认理由（pi，2026-07-30）

**R-03**：Codex 的事实纠正经 Context7 官方文档核实——shadcn 现行文档包含
`radix/`、`base/`、`aria/` 三套组件命名空间，`/components/aria/*` 逐组件提供
`react-aria-components` 安装路径，React Aria 确为 first-class base。本审计方此前
"shadcn 必然封装 Radix"的断言基于过时知识，予以撤回。修订后文本满足 R-03 的核心
诉求（全项目唯一行为层 = React Aria Components），且保留源码脚手架价值。Query 补充
条款（关闭聚焦/重连/轮询、`staleTime: Infinity`、Query stale ≠ 领域 freshness）
与归档 P-002（freshness 只能由 Core 派生）一致，一并接受。图表按实际构建增量裁决
符合预算本意，Recharts 90.10KB gz 的 spike 数据在 ≤120KB 预算内。

**R-04**：取消秘密派生尾缀优于原审计文本——Cookie/API Key 尾部仍属秘密派生片段，
与 §15 检查清单"Rust 返回值不得包含可逆片段"冲突，原审计的尾缀建议系自相矛盾，
予以撤回。标签 + 关联账号数 + 最后验证时间足以消歧，重复标签提示修改即可。窄窗口
帮助区回退（可折叠帮助区替代强制 ≥720px）修正了审计方的过度规格化，接受。
